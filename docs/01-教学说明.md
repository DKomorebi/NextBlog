# NextBlog（一）：全栈项目搭建与 React 入门

## 本系列围绕哪个项目学习

NextBlog 的网站名是「拾页」。它使用 Next.js 展示页面，Express 提供接口，PostgreSQL 保存文章、用户、评论与会话。管理员可以在线发布和修改 Markdown 文章；普通用户可以注册、登录和评论。首页还有文章卡片、搜索分类、分页、Hero 渐显与深浅主题。

本系列直接讲解这套正在运行的全栈代码。第一至八篇按学习顺序建立基础，第九至十四篇深入数据库、认证、页面、组件、主题与测试，第十五篇汇总项目结构和完整源码。文中的路径均相对于 NextBlog 根目录；复制代码时请参考同一版本的配置与锁文件。

| 技术 | 在本项目中做什么 | 先看哪里 |
| --- | --- | --- |
| React | 将文章列表、表单和评论组织成组件 | src/components/full-blog.tsx |
| Next.js | 文件路由、公共布局、构建与接口代理 | src/app、next.config.ts |
| TypeScript | 检查变量、参数、返回值与组件属性 | .ts 与 .tsx 文件 |
| Tailwind CSS / DaisyUI | 工具类、基础控件、主题 | src/app/globals.css |
| Express | 接收请求，检查身份并处理业务 | server/app.ts |
| TypeORM / PostgreSQL | 将对象映射到数据库并持久化 | server/entities.ts、server/db.ts |

## 第一步：安装项目依赖

本项目使用 Node.js 运行 Next.js 和 Express，使用 pnpm 安装依赖。请准备与仓库 Next.js 版本兼容的 Node.js 环境，以及 PostgreSQL。本机开发验证使用 PostgreSQL 18。先确认终端能执行 node、pnpm；数据库可以用已有本地实例，也可以按 compose.yaml 启动一个实例，不要让两个实例争用 5432。


```powershell
git clone https://github.com/DKomorebi/NextBlog.git
cd NextBlog
pnpm install --frozen-lockfile
# 仅首次配置时复制；已有 .env 请保留
Copy-Item .env.example .env
```


package.json 声明依赖范围，pnpm-lock.yaml 固定实际解析结果。--frozen-lockfile 要求安装遵守锁文件；安装不匹配时应查明原因，不要为了绕过错误随意删除锁文件。node_modules 是安装结果，不需要提交。

## 第二步：连接自己的数据库

先在 PostgreSQL 中创建一个空数据库，例如 fieldnotes。连接信息填写到本地 .env；下面只是仓库的占位示例，必须换成自己的数据库账号和密码。

代码位置：`.env.example`（完整文件）。

```text
DATABASE_URL=postgresql://blog:change-this-password@127.0.0.1:5432/fieldnotes
SESSION_SECRET=replace-with-a-random-secret-at-least-32-characters
APP_ORIGIN=http://localhost:3000
API_PORT=4000
API_ORIGIN=http://127.0.0.1:4000
```


DATABASE_URL 同时表达数据库协议、用户名、密码、主机、端口和数据库名。密码包含 @、:、/ 等 URL 特殊字符时需要百分号编码。APP_ORIGIN 是浏览器访问的源；API_ORIGIN 是 Next.js 转发的目标，二者用途不同。不要将数据库密码写成 NEXT_PUBLIC_ 开头的环境变量。

SESSION_SECRET 用于会话签名，至少 32 个字符。下面的命令生成随机值，将输出保存到你自己的 .env，不要提交这个值。


```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

```powershell

```


迁移负责创建表和索引；seed 可选，导入六篇示例文章，遇到已有 slug 会跳过。dev 同时启动 3000 端口的 Next.js 和 4000 端口的 Express。打开 http://localhost:3000 阅读文章，不要把前端端口换成 127.0.0.1 却仍保留不同的 APP_ORIGIN。

注册后默认是普通用户。要学习文章管理，先注册自己的邮箱，再在项目终端执行 `pnpm admin 你的注册邮箱`，刷新浏览器进入“管理”。没有默认管理员密码。

## 从首页认识 React 组件

代码位置：`src/app/page.tsx`（完整文件）。

```tsx
import { ArticleList } from "@/components/full-blog";
export default function Home() {
  return <ArticleList />;
}
```


Page 是一个返回 JSX 的函数。JSX 看起来像 HTML，但允许用大括号嵌入 JavaScript 表达式；首字母大写的 ArticleList 表示另一个组件。import 引入的是函数定义，`<ArticleList />` 表示在页面中渲染它。

ArticleList 也用于归档页和管理页，通过 archive、manage 属性选择界面。这些传入组件的参数称为 props。列表内部的搜索词和页码则使用 state 保存，用户输入后由 React 更新界面。后面会分别学习 props、state 和异步请求。

# NextBlog（二）：Next.js 路由、布局与前后端边界

## 文件路径怎样变成网址

项目使用 App Router。src/app 下的文件夹代表路径段，page.tsx 是页面入口，layout.tsx 包裹子页面。组件文件放进 src/components 不会自动产生网址。

| 网址 | 页面文件 | 主要组件 |
| --- | --- | --- |
| / | src/app/page.tsx | ArticleList |
| /archive | src/app/archive/page.tsx | ArticleList archive |
| /about | src/app/about/page.tsx | 关于页正文 |
| /posts/文章标识 | src/app/posts/[slug]/page.tsx | ArticleReader |
| /login、/register | 对应目录的 page.tsx | AuthForm |
| /admin | src/app/admin/page.tsx | ArticleList manage |
| /admin/new | src/app/admin/new/page.tsx | Editor |
| /admin/文章ID | src/app/admin/[id]/page.tsx | Editor id |

slug 是便于阅读的唯一文章标识，例如 my-first-post；id 是数据库 UUID。阅读接口按 slug 查询，修改和删除按 id 操作。管理列表生成编辑链接时还带 slug 查询参数，Editor 加载后会验证返回的文章 id 与路径一致。

## 动态参数为什么需要 await

代码位置：`src/app/posts/[slug]/page.tsx`（完整文件）。

```tsx
import { ArticleReader } from "@/components/full-blog";
export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  return <ArticleReader slug={(await params).slug} />;
}
```


方括号表示动态路径段。本项目采用的 Next.js 版本把 params 声明为 Promise，因此页面是 async 函数，先 await 再取 slug。这里仅将标识传入 ArticleReader；真正加载文章正文的请求在客户端组件中执行。不能看到 async 页面就认为正文已经在服务端读取了。

## 公共布局负责稳定的页面外框

代码位置：`src/app/layout.tsx`（完整文件）。

```tsx
import type { Metadata } from "next";
import { Header, SessionProvider } from "@/components/full-blog";
import "./globals.css";
import { themeInitScript } from "@/lib/theme";
export const metadata: Metadata = {
  title: { default: "拾页 · 落笔成文，拾页成光", template: "%s · 拾页" },
  description: "关于技术、生活与每一个值得记录的想法。",
};
export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="zh-CN" data-theme="fieldnotes" suppressHydrationWarning>
      <head>
        <script dangerouslySetInnerHTML={{ __html: themeInitScript }} />
      </head>
      <body>
        <SessionProvider>
          <Header />
          <main className="site-main">{children}</main>

            <span>拾页</span>

```


children 是当前路由渲染出来的内容。Header、页脚和 SessionProvider 放在布局中，让页面共享外框和登录状态。metadata 提供基础标题与描述；当前文章标题没有在这个布局中自动变成每篇文章的独立 SEO 元信息。

head 中的脚本来自本地固定字符串 themeInitScript，用于绘制前确定深浅主题。这里没有插入用户文章。suppressHydrationWarning 只用于 html 上预先改变的主题属性，不是忽略所有界面错误的开关。

## Server Component 与 Client Component

app 中没有标记的组件默认处于服务端组件模型。本项目 full-blog.tsx 和 theme-toggle.tsx 顶部的 `"use client"` 建立客户端边界，使它们能使用 state、effect、点击事件等能力。它们仍可能参与首屏预渲染，浏览器对象应在合适的 effect 或事件中访问。

服务端布局可以把 children 传给客户端 Provider；这不意味着所有 children 都被改写成客户端组件。应沿 import 边界和组件职责判断。数据库模块只在 server 目录的后端入口使用，不导入浏览器业务组件。

## 为什么浏览器只请求 /api

代码位置：`next.config.ts`（完整文件）。

```typescript
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  distDir: ".next-fullstack",
  async rewrites() {
    return [
      {
        source: "/api/:path*",
        destination: `${process.env.API_ORIGIN || "http://127.0.0.1:4000"}/api/:path*`,
      },
    ];
  },
};

export default nextConfig;
```


浏览器请求 localhost:3000/api/articles，Next.js 将请求转发至 Express 的 4000 端口。地址栏保持网站的同一源，api() 使用 same-origin 携带 Cookie。代理不会替代身份检查；真正的权限判断仍在 Express 中。

API_ORIGIN 是服务器连接目标，APP_ORIGIN 则参与写请求的来源校验。改变访问端口后，要同步调整配置并重启服务；生产环境应配好 HTTPS、转发头与受控代理链。

## 构建结果要怎样理解

pnpm build 输出 .next-fullstack。部分页面可以预渲染出外框，然后在浏览器请求数据库内容；这不代表整个项目能够仅靠静态文件运行。当前应用需要 Next.js 服务、Express 和 PostgreSQL。

未找到文章时 API 返回 404，ArticleReader 显示错误；当前实现没有将这个客户端结果转换成详情文档本身的 HTTP 404。src/app/not-found.tsx 用于 Next.js 未匹配路由等情况。若以后重构正文服务端获取，应一起处理 notFound、标题与缓存策略。

## 练习

对照路由表打开每个页面，在 Network 面板观察页面导航与 /api 请求的区别。然后从首页进入文章，沿 page.tsx → ArticleReader → api() → Express 依次找到执行位置。


# NextBlog（三）：用真实业务理解 TypeScript

## 类型解决什么问题

JavaScript 在运行时执行请求与渲染；TypeScript 在开发、检查和构建阶段帮助发现不一致。它不会自动证明接口返回的数据正确，也不会代替登录权限检查。先从真实业务对象学习，比单独背语法更容易理解。

代码位置：`src/components/full-blog.tsx`（节选）。

```tsx
type User = {
  id: string;
  username: string;
  email: string;
  role: "user" | "admin";
};
type Session = { user: User | null; csrf: string };
type Article = {
  id: string;
  slug: string;
  title: string;
  excerpt: string;
  content: string;
  category: string;
  createdAt: string;
  version: number;
};
type Comment = {
  id: string;
  userId: string;
  username: string;
  content: string;
  createdAt: string;
};
```


User 的 role 是联合类型，只允许 user 或 admin；Session.user 是 User 与 null 的联合，因为游客也有会话。Article.id 和 slug 都是字符串，但业务含义不同。createdAt 在浏览器 API 类型中是字符串，而服务器实体使用 Date，因为 HTTP JSON 传输会将日期序列化。

这里的 Article 类型在列表和详情中复用，但列表接口为了节省流量没有返回 content。当前列表不读取正文，因此界面可以工作；若继续拆分类型，应定义只含列表字段的 ArticleSummary，而不是依靠一个宽泛类型假设每次都有正文。这也是阅读现有代码时要认识的改进空间。

## 可空值、可选参数与安全访问

`session.user?.role` 先检查 user 是否存在，游客不会因为直接取 null.role 而报错。`register?: boolean` 表示调用方可以不传；AuthForm 的默认值 false 将它解释为登录页。`Editor({ id }: { id?: string })` 用 id 是否存在区分新建和编辑。

可选链只是取值语法，不提供权限保障。浏览器可以修改自己的状态，后端必须再次读取登录身份与角色。后端的 `req.account!` 是非空断言，表示开发者相信前置中间件已保证登录；这个符号不会在运行时创建账号或检查权限。

## 泛型让请求返回值有类型

代码位置：`src/components/full-blog.tsx`（节选）。

```tsx
async function api<T>(
  path: string,
  method = "GET",
  body?: unknown,
  csrf?: string,
): Promise<T> {
  const r = await fetch("/api" + path, {
    method,
    credentials: "same-origin",
    cache: "no-store",
    headers: {
      "Content-Type": "application/json",
      ...(csrf ? { "X-CSRF-Token": csrf } : {}),
    },
    ...(body ? { body: JSON.stringify(body) } : {}),
  });
  if (r.status === 204) return undefined as T;
  const data = await r.json().catch(() => ({ message: "服务响应异常" }));
  if (!r.ok)
    throw new Error(data.details?.join("；") || data.message || "请求失败");
  return data;
}
```


T 是调用方传入的类型参数。例如 `api<Session>("/auth/session")` 让后续代码知道应读取 user 和 csrf。Promise<T> 表示异步完成后得到 T。body 使用 unknown，意味着封装允许接收不同业务参数，而不会在函数内擅自假设某个字段。

204 响应没有 JSON 正文，函数直接返回；其余响应先解析 JSON，再根据 r.ok 决定返回还是抛错。泛型本身没有验证 JSON 的形状，`undefined as T` 也只是断言。因此调用删除接口的地方不能继续读取返回对象；更严格的封装可以区分有正文与无正文的响应。

## keyof 与 typeof 如何约束表单

代码位置：`src/components/full-blog.tsx`（节选）。

```tsx
  function change(key: keyof typeof blank, value: string) {
    dirty.current = true;
    setForm((f) => ({ ...f, [key]: value }));
  }
```


typeof blank 取得初始表单对象的类型，keyof 再取出 title、slug、excerpt、category、content 这些键的联合。因此 change("title", value) 合法，拼错成 change("titel", value) 会在类型检查时报错。

`[key]` 是计算属性名，`{ ...f, [key]: value }` 创建新对象并替换一个字段。传函数给 setForm 可以基于最近的状态更新，而不是依赖某次渲染捕获的旧对象。dirty 是 ref，标记未保存变化；它的变化不直接触发界面重新渲染。

## 输入验证要在运行时再做一次

代码位置：`server/app.ts`（节选）。

```typescript
const articleInput = z
  .object({
    title: z.string().trim().min(1).max(160),
    slug: z
      .string()
      .regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/)
      .max(120),
    excerpt: z.string().trim().max(500),
    category: z.string().trim().min(1).max(40),
    content: z.string().trim().min(1).max(200000),
  })
  .strict();
```


Zod 的 parse 在接口收到请求时实际执行。title 去掉两侧空格后不能为空，slug 只能由小写英文、数字和连字符构成，content 有长度上限，strict 拒绝额外字段。前端的类型、input 的 required 与后端的 parse 分别承担不同层面的检查。

数据库还有唯一约束、非空约束和外键，即使并发请求通过了前面的检查，也不能保存重复 slug 或无效关联。完整的数据保障横跨 TypeScript、Zod 和数据库约束。

## 工程配置与练习

tsconfig.json 开启 strict，noEmit 表示类型检查不额外生成 JavaScript；Next.js 负责应用构建。paths 将 @/* 映射到 src/*，所以 @/components/full-blog 指向 src/components/full-blog.tsx。带 JSX 的文件使用 .tsx，普通逻辑和类型文件通常使用 .ts。

练习时在临时编辑中把 role 写成不存在的值、把表单键拼错，然后运行 pnpm typecheck 观察错误并撤销。再思考：直接通过 HTTP 发出非法 role 时为什么仍必须由后端拒绝？答案是 TypeScript 不运行在外部请求上。


# NextBlog（四）：Tailwind CSS、DaisyUI 与简约页面

## 三种样式工具各自负责什么

Tailwind CSS 提供原子工具类，例如 sr-only 和 whitespace-pre-wrap。DaisyUI 在 Tailwind 上提供 btn、input、select、card 等组件类。globals.css 中的 article-card、home-hero 和 header-inner 则控制本站的排版与布局。

读到 `className="btn btn-primary"` 时，btn 表示按钮基础规则，btn-primary 使用主题主色。读到 article-card 时，应到 globals.css 找项目自定义样式。当前项目使用了不少语义 CSS 类，不是把每条样式都写成 Tailwind 工具类。

```tsx
          开始阅读
        </a>
      </div>
    </section>
  );
}
```


这个组件负责语义内容：一个主标题、一句介绍、一个阅读锚点。排版宽度、间距、渐显时机在 globals.css 中控制。标题分成两行并只强调部分文字，可以在少量内容下建立视觉层级。

`href="#articles"` 跳到文章区域，不触发新的后端业务。CSS 在 prefers-reduced-motion 条件下关闭渐显并显示内容，避免读者因为减少动态效果设置而看不到文字。动画应作为补充，不能承担内容是否可读的职责。

## 文章卡片与响应式布局

ArticleList 渲染每篇文章时使用 article-card，同时保留标题链接、摘要、分类与日期。卡片用细边框、圆角和轻微悬停反馈区分内容，不再需要大段装饰性说明文字。分类标签使用 DaisyUI badge，辅助图标来自 lucide-react。

桌面文章区域使用网格，700px 以下切成单列。手机导航允许换行，主题按钮放在品牌右侧；搜索框与分类控件要共同适应可用宽度。仅观察桌面缩略图不够，还要实际检查 375px 下文档宽度是否超出视口。

## 图标、标签与可访问名称

Search、Folder、CalendarDays、Pencil、Trash2 等图标对应搜索、分类、日期、编辑和删除。旁边已有文字的图标设置 aria-hidden，避免屏幕阅读器重复朗读。主题按钮只有图标，所以由 aria-label 提供“切换深色主题”或“切换浅色主题”。

搜索框的说明使用 sr-only：视觉上隐藏，但仍为输入框提供名称。不要将所有小字一律删除；重复装饰文案可以精简，密码要求、错误提示与控件标签仍然影响用户完成操作。

## 深浅主题不只是 CSS

theme.ts 在首帧读取主题偏好，ThemeToggle 处理点击、系统偏好、跨标签同步及 localStorage。支持 View Transition 的浏览器使用圆形展开；不支持或开启减少动态效果时直接切换。第十三篇逐段解释这一实现。

练习：调整主题 primary 后检查按钮、图标和标签；再切到深色检查正文、边框、输入框、代码块和错误状态。调整卡片间距时同时检查桌面与手机，不要只扩大固定宽度。


# NextBlog（五）：React 状态、搜索请求与表单交互

## 从一次输入理解状态更新

ArticleList 用 q 保存搜索词，用 category 保存分类，用 page 保存页码，用 items 和 total 保存接口结果。输入框的 value 来自 q，onChange 调用 setQ；这种由 React 状态决定输入值的方式称为受控输入。

修改搜索词或分类时同时 setPage(1)，因为原来第十页在新的筛选条件下可能不存在。不要先修改数组或 DOM 再试图让 React 猜出变化；应改变状态，让渲染从状态生成界面。

## useEffect 把状态变化连接到请求

代码位置：`src/components/full-blog.tsx`（节选）。

```tsx
  useEffect(() => {
    let alive = true;
    const timer = setTimeout(() => {
      setBusy(true);
      api<{ items: Article[]; total: number }>(
        `/articles?q=${encodeURIComponent(q)}&category=${encodeURIComponent(category)}&page=${page}`,
      )
        .then((r) => {
          if (alive) {
            setItems(r.items);
            setTotal(r.total);
            setError("");
          }
        })
        .catch((e) => {
          if (alive) setError(e.message);
        })
        .finally(() => {
          if (alive) setBusy(false);
        });
    }, 200);
    return () => {
      alive = false;
      clearTimeout(timer);
    };
  }, [q, category, page, revision]);
```


依赖数组中的 q、category、page 或 revision 变化时，React 清理上次 effect，再启动本次 effect。200ms 定时器减少连续输入时的请求频率。清理函数取消尚未触发的定时器，并将本次闭包中的 alive 改为 false。

alive 解决的是响应先后顺序：旧搜索即使较晚返回，也不能覆盖新搜索。它不会中止已经发出的 HTTP 请求；如果需要节省请求传输，还应使用 AbortController。这段代码区分了“忽略过期结果”和“取消网络任务”。

encodeURIComponent 将用户输入编码到 URL 参数中；后端再用 Zod 检查长度，用参数绑定查询数据库。浏览器编码并不等于 SQL 注入防护，两个环节各自解决不同问题。

## loading、empty 和 error 是不同状态

busy 控制加载反馈，items 为空且没有错误时显示空列表，error 非空时显示错误与重试按钮。不要在请求尚未完成时立即显示“没有文章”，也不要把数据库错误解释成搜索结果为空。

revision 是重新加载的触发值。删除成功或点击重试时递增它，effect 因依赖改变而重新读取结果。分页按钮依据 total 和每页 10 条计算边界；当前排序由后端固定为创建时间倒序，没有独立的前端排序选择器。

## 多个页面如何共享登录状态

代码位置：`src/components/full-blog.tsx`（节选）。

```tsx
export function SessionProvider({ children }: { children: ReactNode }) {
  const [session, setSession] = useState<Session>({ user: null, csrf: "" }),
    [loading, setLoading] = useState(true),
    [error, setError] = useState("");
  async function refresh() {
    try {
      setSession(await api<Session>("/auth/session"));
      setError("");
    } catch (e) {
      setError((e as Error).message);
    } finally {
      setLoading(false);
    }
  }
  useEffect(() => {
    void refresh();
  }, []);
  return (
    <Context.Provider value={{ session, loading, error, refresh, setSession }}>
      {children}
    </Context.Provider>
  );
}
```


SessionProvider 只负责读取和共享当前会话，Header、AuthForm、Comments 与 Editor 通过 useContext 获取状态。loading 表示首次验证尚未完成，error 表示连接失败；游客的 user 为 null，不等于网络请求失败。

登录或注册成功后，AuthForm 用 setSession 接收服务器返回的公开用户信息与新 CSRF token，再通过 router.push 返回首页。退出后 Header 调用 refresh 重新读取游客会话。Cookie 由浏览器管理，React 状态只是用于显示的当前快照。

## 表单提交为什么不直接刷新页面

AuthForm 在 onSubmit 中调用 preventDefault，阻止浏览器按传统表单导航；然后用 FormData 读取 email、password 和可选昵称，交给 api() 发送 JSON。Editor 则使用受控对象保存文章字段，因为它还需要预览和导入正文。

busy 在请求期间禁用提交，finally 恢复按钮。错误时保留输入并展示说明，不能先清空正文再发送请求。服务端会独立检查数据和权限，前端禁用按钮不能阻止他人直接调用接口。

## useRef 与 useState 的差异

Editor.dirty 和 ThemeToggle.inFlight 不直接决定一段文字内容，而是供事件处理读取的标志，使用 ref 保存。useRef 的 current 改变不会触发渲染；dark、busy 等会改变按钮外观的值则使用 state。

练习：将 Network 设置为较慢速度，快速输入两次不同关键词，观察较旧请求的结果不会覆盖最新结果。再临时停止自己启动的后端，检查“连接失败”和“没有文章”是否能被区分，恢复后使用重试。
