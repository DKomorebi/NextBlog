# 注册与邮箱验证：从页面事件到数据库事务

本次改动参考 SSM_demo 的 `Register.vue`、`UserRegisterDTO.java`、`UserController.java` 和 `EmailService.java`。流程是：填写邮箱 → 获取验证码 → 填写昵称、密码和确认密码 → 提交验证码 → 后端创建用户 → 自动登录。

邮箱验证码用于证明当前注册者能够接收这个邮箱的邮件。确认密码用于防止用户误输入密码。两者解决不同问题，必须分别校验。这里实现的是**注册时邮箱所有权验证**，不是每次登录的双因素认证。

## 1. 文件从哪里读

| 文件 | 负责的工作 |
| --- | --- |
| `src/components/full-blog.tsx` 中的 `AuthForm` | 注册/登录表单，确认密码，发送按钮，倒计时，错误提示 |
| `server/app.ts` | 定义接口，校验请求结构、确认密码、CSRF 和 IP 限流，建立登录 Session |
| `server/registration.ts` | 发送名额、验证码生成和摘要、过期判断、错误次数、注册事务 |
| `server/mail.ts` | 根据环境变量创建 Nodemailer SMTP 发送函数 |
| `server/registration-migration.ts` | 创建注册验证码表和清理索引 |
| `server/db.ts` | 将新迁移注册到 TypeORM DataSource |
| `server/index.ts` | 把真实邮件发送函数注入应用 |
| `server/registration.test.ts` | 注册安全边界与并发的 PostgreSQL 集成测试 |
| `server/app.test.ts` | 注册成功之后的 Session、权限、文章与评论回归测试 |

`server` 仍然使用根目录的 `package.json` 和 `node_modules`，没有单独建立第二套依赖目录。新增依赖是 `nodemailer`，开发时使用 `@types/nodemailer` 提供类型信息。

## 2. 为什么页面里能处理事件

`full-blog.tsx` 第一行是 `"use client"`。它声明这个模块作为客户端组件入口，内部可以使用 React 状态和浏览器事件。Next.js 没有要求把注册表单写成没有事件的页面。本项目实际使用的是 React 的表单事件与普通 HTTP API，未采用 Server Actions。

关键代码是：

```tsx
<form ref={formRef} onSubmit={submit}>
  {/* 各个输入框 */}
  <button type="button" onClick={sendCode}>发送验证码</button>
  <button className="btn btn-primary">注册并登录</button>
</form>
```

`onSubmit={submit}` 将提交事件绑定到 `submit` 函数；用户点击提交按钮或在输入框中按 Enter，都会经过同一处逻辑。`e.preventDefault()` 阻止浏览器执行传统的整页表单提交，然后我们调用 `api()` 向 Express 发送 JSON。

发送按钮的 `type="button"` 很重要。如果省略，表单内按钮默认为提交按钮，用户点击“发送验证码”也会触发注册提交，并被昵称、密码等尚未填写的必填项拦住。

这里的输入框主要是非受控输入：使用 `name` 标识字段，提交时通过 `new FormData(e.currentTarget)` 读取。因此看不到每个输入框都配一份 `useState` 和 `onChange`。非受控输入仍然具有事件，也能使用浏览器原生的 `required`、`minLength`、`pattern` 校验。

验证码发送只需要邮箱，所以 `sendCode()` 用 `formRef.current.elements.namedItem("email")` 取得邮箱输入框，再调用 `reportValidity()`。此时不会要求用户先填完其他字段。

确认密码在提交时先比较：

```tsx
if (register && password !== f.get("confirmPassword")) {
  setError("两次输入的密码不一致，请重新确认");
  // 实际代码还会把焦点移到确认密码输入框。
  return;
}
```

前端比较用于立即提示用户。请求体还会传递 `confirmPassword`，后端通过 Zod 的 `refine` 再检查一次；绕过浏览器不能绕过后端校验。确认密码不会保存到数据库，用户表只保存密码的 bcrypt 哈希。

邮箱修改时，`onChange` 会清空已填写的验证码和发送提示，避免把旧邮箱验证码误用于新邮箱。验证码归属最终由后端判断，并不依赖这个页面行为。

倒计时用 `useState` 显示剩余秒数，以截止时间减去 `Date.now()` 计算，而不是把“点击次数”当作限制。`useRef` 中的发送锁避免连续点击触发多个正在执行的请求。刷新页面会丢失显示倒计时，但数据库中的限流记录还在，所以不能借刷新绕过限制。

## 3. 接口与返回值

两个 POST 接口都继承项目已有的同源 `Origin` 和 `X-CSRF-Token` 校验。先访问 `GET /api/auth/session`，保留 Session Cookie，并使用返回的 `csrf`。

### 3.1 获取注册验证码

```http
POST /api/auth/register/code
Content-Type: application/json
Origin: http://localhost:3000
X-CSRF-Token: <从 session 接口获得>
```

```json
{ "email": "reader@example.com" }
```

成功时返回 `200`、提示文字和 `retryAfter: 60`，**不会在响应中包含验证码**。邮箱会先去掉首尾空格并转为小写。邮箱格式不正确返回 `400`，频率超限返回 `429`，邮件未配置或发送失败返回 `503`。

已注册邮箱收到同样的成功提示，但不发送注册验证码；用户应使用已有账号登录。统一响应文字降低直接枚举账号的便利性，不过这个实现没有保证所有分支耗时完全相同。

### 3.2 完成注册

```json
{
  "email": "reader@example.com",
  "username": "读者",
  "password": "example-password-123",
  "confirmPassword": "example-password-123",
  "verificationCode": "123456"
}
```

示例数字仅用于展示请求结构，无法代替真实邮件验证码。代码必须是 6 位数字字符串，保留可能存在的前导零。密码至少 10 个字符，最多 72 字节；确认密码必须与原密码完全相同。

后端不接受客户端设置 `role`，新账号固定是普通用户。成功返回 `201` 和 `{ user, csrf }`，重建 Session，更新 Cookie，然后前端跳转首页。验证码缺失、错误、过期或已消费都不能创建账号。

登录接口仍只接收邮箱和密码，不要求重新输入确认密码或注册验证码。

## 4. 验证码为什么需要数据库

SSM_demo 用内存 Map 保存验证码。本项目改为 PostgreSQL 表 `registration_codes`，以邮箱作为主键：

| 字段 | 含义 |
| --- | --- |
| `email` | 规范化邮箱，一行对应一个邮箱 |
| `nonce` | 本次发送的随机 UUID，用于区分重发前后的验证记录 |
| `digest` | 邮箱、nonce 和验证码的 HMAC-SHA256 摘要，空值表示不可用 |
| `expires_at` | 发送成功后 5 分钟的失效时间 |
| `attempts` | 本轮错误验证次数，达到 5 次即失效 |
| `sent_at` | 预留本次发送名额的时间，用于 60 秒冷却 |
| `window_at`、`sends` | 当前固定 1 小时发送窗口的起点与发送次数，最多 5 次 |

验证码由 `crypto.randomInt` 生成，而不是 `Math.random()`。数据库不保存明文验证码；HMAC 使用服务器端的 `SESSION_SECRET` 作为密钥，并包含用途、邮箱和 nonce。低熵数字验证码不适合只用无密钥哈希，因为数据库泄漏后很容易枚举全部 100 万种输入。

`SESSION_SECRET` 变化后，未使用的旧验证码会失效。它必须保存在服务端环境变量中，不可使用 `NEXT_PUBLIC_` 前缀。

邮件发出之前，服务用一条带条件的 `INSERT ... ON CONFLICT DO UPDATE` 原子占用名额。两个请求同时申请同一邮箱，只会有一个通过。每个邮箱每个固定小时窗口最多申请 5 次，窗口内每次间隔至少 60 秒。

成功申请重发会先使旧验证码失效。SMTP 发送发生在数据库事务之外，避免长时间占用事务等待外部网络。只有发送成功后才写入有效摘要与过期时间。SMTP 失败时保留配额，但不产生有效验证码；这样不能利用反复失败绕过发送限制。若 SMTP 成功后数据库更新失败，该邮件的验证码无法使用，用户需要稍后重新发送。

每次发送请求会清理一天以前的旧记录。注册成功会清空摘要与过期时间，但暂时保留发送计数。

IP 层还有 `express-rate-limit` 的每小时 10 次发送接口限制，失败请求也计数。目前 IP 计数保存在单个 API 进程内；邮箱计数在数据库中。若部署多个 API 实例，应为 IP 限流配置共享存储，同时检查反向代理的真实 IP 信任范围。

## 5. 为什么注册需要事务和行锁

核心流程在 `createRegistration().register()` 中：

1. 开启 TypeORM 事务，用 `SELECT ... FOR UPDATE` 锁住这个邮箱的验证码记录。
2. 检查是否存在有效摘要、是否过期、错误次数是否达到 5 次。
3. 计算输入验证码的摘要，使用 `timingSafeEqual` 比较。
4. 验证失败时更新错误次数，并正常提交事务，随后在事务外返回业务错误。
5. 验证成功时计算密码哈希、保存用户，并清空验证码摘要；一起提交事务。

第 4 步容易写错。如果先更新错误次数，然后在事务回调内部抛异常，TypeORM 会回滚更新，错误次数永远不会增加。因此实现选择返回 `null`，让事务提交后再抛出 `RegistrationError`。

第 5 步保证“创建用户”和“消费验证码”一致。并发提交时，第一个请求创建成功并清空摘要；第二个请求获得行锁后看到摘要已空，返回失败，不会重复注册。用户邮箱的唯一约束也是最后一道保障。

本次迁移只新增验证码表，不会修改旧用户的登录权限，也没有把旧账号伪标记为已验证。新注册强制验证，旧账号仍可登录；若以后要求旧账号也验证邮箱，需要另行增加绑定或补验证流程。

## 6. SMTP 配置和运行步骤

在根目录 `.env` 添加：

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=sender@example.com
SMTP_PASS=replace-with-smtp-authorization-code
SMTP_FROM=sender@example.com
```

这里全部是占位值。真实配置只放在 `.env`，不要提交到仓库。对于需要授权码的邮箱，`SMTP_PASS` 应使用该服务提供的 SMTP 授权码。

`server/mail.ts` 在端口 465 使用隐式 TLS；其他端口使用强制 STARTTLS，不关闭证书验证。具体含义见 [Nodemailer SMTP 文档](https://nodemailer.com/smtp)。代码设置了连接、问候和通信超时，发送失败只向网页返回业务提示，不回传包含账号信息的 SMTP 原始错误。

`createRegistrationMailer()` 返回一个函数，`server/index.ts` 将它传给 `createApp`。这就是依赖注入的一个小例子：业务代码只依赖“把验证码发给邮箱”的能力，不直接读取 SMTP 密码。集成测试传入内存收件箱函数，因此不会误发真实邮件；生产入口没有测试验证码或跳过验证的分支。

拉取此版本后运行：

```powershell
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm dev
```

如果开发服务已经启动，修改 `.env` 后重启。数据库迁移只需执行一次，再次运行会跳过已执行的迁移。

在注册页填写邮箱，点击“发送验证码”，查收邮件后完成其余字段并提交。如果请求显示 `503`，先检查 SMTP 配置及授权码；如果显示 `429`，等待冷却或小时窗口结束。若邮箱已有账号，应转到登录页。

## 7. 如何验证修改

```powershell
pnpm typecheck
pnpm test:api
pnpm build
```

接口测试会创建随机命名的独立 PostgreSQL 测试数据库，结束时清理，不使用现有博客数据。测试覆盖以下业务边界：

- 无 CSRF、非法邮箱、缺少验证码、缺少确认密码、密码不一致、非法角色参数。
- 邮箱规范化、验证码只适用于对应邮箱、摘要存储、返回值不泄露验证码。
- 错误 5 次失效、5 分钟过期、重发后旧码失效、注册后重放失败。
- 并发发送只能成功一次，并发注册只能创建一个用户。
- 服务重建后仍能校验、发送冷却、邮箱小时配额、IP 限流。
- SMTP 失败时没有可用验证码，错误响应不包含底层敏感信息。
- 注册成功后原有 Session、管理员权限、文章、评论和登录退出流程仍然正常。

浏览器验收还应检查：仅填写邮箱便可发送；按钮倒计时禁用；修改邮箱清空验证码；密码不一致时定位确认密码输入框；按 Enter 提交；手机宽度下表单不横向溢出；登录页不出现注册专属字段。

本次本地验证已通过类型检查、两个 PostgreSQL 集成测试、生产构建以及使用模拟 API 的浏览器交互测试。SMTP 已验证连接和认证，但这不等于邮件已经投递到收件箱；首次真实注册仍需检查实际收件情况。
